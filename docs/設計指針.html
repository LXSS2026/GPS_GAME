GPS 設計指針

置き場: E:\VSC_Git\GPS 。方針の変更はこの文書を更新してから実装する。

1. ゲームの柱

  • ボクセル世界の上で、都市運営(SimCity 型)・立体工場(上下方向にも組める)・ロボット製造(世代別)・戦争または外交を一つの経済で回す。
  • 視点は俯瞰の管理視点。一人称で掘る遊びは含めない。
  • 軍人は都市の内政で徴用する。戦争か外交かはプレイヤーが選ぶ。

2. 技術構成

部分手段
描画・入力・UIGodot 4.7 (.NET 版) + C#。game/ 配下。エンジン実体は .tools/(git 管理外)。
計算本体(世界・工場・都市・戦争・外交)エンジン非依存の .NET ライブラリ sim/GPS.Sim。Godot を参照しない。
検証sim/GPS.Sim.Tests(xunit)。描画は ++ --screenshot <path> [--click x,y] [--rclick x,y] で画面を保存して目視。
定義データ(ブロック・レシピ・機械・ロボ世代・政策)game/data/*.json。コードに定数を埋めない。
ボクセル描画自前のチャンクメッシュ化(隣が空気の面だけ出す)。既製ライブラリは C# 非対応のため使わない。

3. 守る原則

  • 入力は全てコマンド(ICommand)として投入し、固定ティック(60/秒)で順に適用する。同じコマンド列は同じ結果になる(決定論)。これがマルチプレイ(ロックステップ)の前提。マルチプレイ自体は最初の実装では作らない。
  • Godot 側は「状態を読んで描く」「入力をコマンドに変換して渡す」だけ。ゲームの判断を Godot のノードに書かない。
  • 四つのサブシステムは一つのティックループと一つの資源台帳を共有する。

4. 確定している要件

項目内容決定日
製品の品質と歩留まり工場の生産物には歩留まりと品質のばらつきがある。一定以上のレベルや世代のロボットを作るには、一定以上の品質の製品が必要。製品は品質値を持つ個体として流れ、レシピは入力の品質下限を持つ方向で手順 2 の設計時に具体化する。2026-10-14

5. 作る順番

手順内容状態
1ボクセル世界にブロックを置ける(描画・カメラ・設置と撤去)完了 2026-10-14
2工場の核(ベルト・インサータ・機械を上下方向にも組める)。品質・歩留まりを含む未着手
3工場の産出物からロボットを世代別に製造する未着手
4都市(人口・雇用・税)。労働力と徴兵を工場・軍に供給する未着手
5戦争(同じボクセル地図上の RTS)、その後に外交未着手
